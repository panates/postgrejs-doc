# Benchmarks

postgrejs is benchmarked against `pg` (node-postgres) and `postgres` (postgres.js) on the same PostgreSQL server, same machine, same workload. Numbers below are a snapshot from the project's `doc/BENCHMARKS.md` (generated by `npm run bench:report`) — **they are version/environment-specific and will drift**. For current numbers, regenerate them yourself or check the source repo's `doc/BENCHMARKS.md`.

## Methodology

- Each scenario is implemented once per library, using that library's own idiomatic/fastest calling convention (not a shared lowest-common-denominator `query(sql, params)` call), while all three read identical SQL text, row counts, and concurrency/pool-size knobs from `benchmark/scenarios/*.ts`.
- Each `(library, scenario)` pair runs in its own child process, spawned sequentially (never in parallel), to avoid CPU/connection contention and get clean V8 JIT warm-up per run.
- The default matrix runs each pair 3 repeats; tables report the **median across repeats**, with intra-run p75/p99 latency and ops/sec from tinybench's sample statistics.
- Each table also reports **GC (ms/op)** (garbage-collection time per timed sample, a proxy for allocation churn) and **Peak Heap (KB)** (the highest heap-above-baseline observed during the whole scenario run, not a per-call figure). Both are directional, not as precise as latency.
- Two scenarios (Large Blob Fetch, Large Array Fetch) also report **Network (KB/op)** — bytes received at the socket, since that's where binary vs. text wire format actually separates the libraries.

### Disclosed asymmetries

The methodology deliberately does not force every library into an identical code path where that would misrepresent a library's real capability. Notable cases:

- **Pool concurrency** — postgres.js's automatic pipelining and postgrejs's opt-in `pipeline: true` are both exercised as real features; `pg` has no equivalent and runs one query per connection.
- **Cursor streaming** — `pg` has no built-in cursor API; its scenario emulates one with raw `DECLARE CURSOR` / `FETCH n` / `CLOSE`.
- **Prepared-statement reuse** — postgres.js auto-prepares, `pg` uses a named statement, postgrejs uses explicit `prepare()`/`execute()`/`close()`.
- **Type decoding** — no custom type parsers/overrides for any library; each uses its own default row shape (e.g. `pg` returns `int8` as a string, postgres.js as `BigInt`).
- **Row shape** — postgrejs's `objectRows` option is explicitly set `true` to match `pg`/postgres.js's default object-row output (the one deliberate normalization).
- **Binary protocol** — postgres.js has no binary protocol support at all; `pg`'s binary parser table is missing or buggy for several types exercised here (`varchar`/`json`/`jsonb`/`bytea` unregistered; `_int4` registered but wrong on negative values). Those libraries are excluded from binary-only comparisons rather than reported with corrupted/misleading numbers.
- **`pg-native`** is out of scope (requires system libpq + native compilation).

See the source repo's `benchmark/README.md` and `doc/BENCHMARKS.md` for the full list of disclosed asymmetries.

### Notable qualitative findings

- postgrejs's binary protocol is its Extended Query default; postgres.js has no binary support and `pg`'s binary decoders are missing or incorrect for several common types (`varchar`/`json`/`jsonb`/`bytea` unregistered; `_int4` mishandles negative values and desyncs element counts on larger arrays).
- Binary format roughly halves wire bytes for `bytea` versus text (hex-encoded, 2 characters/byte), which shows up directly in the Large Blob Fetch network-bytes figures.
- Peak-heap growth is consistently lower for postgrejs across most scenarios, per the source report's per-scenario tables.

## Reproducing the Benchmarks

Benchmarks live in the [postgrejs](https://github.com/panates/postgrejs) repo's `benchmark/` folder, not in this docs project.

1. Start a PostgreSQL server via the repo's `docker/docker-compose.yml`:
   ```bash
   docker compose -f docker/docker-compose.yml up -d postgres
   ```
2. Run the full matrix (every scenario, every library, 3 repeats):
   ```bash
   npm run bench
   ```
3. Regenerate `doc/BENCHMARKS.md` from the latest results:
   ```bash
   npm run bench:report
   ```

Useful flags:

- `npm run bench -- --scenario=simple-query-execute --lib=pg,postgrejs --repeats=1` — fast iteration on a single scenario/library subset.
- `--repeats=10` — more repeats for a more defensible median before publishing numbers.
- `BENCH_BULK_ROWS=500000 npm run bench` — more rows for the cursor-stream scenario.

Connection settings are read from `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`/`PGDATABASE`; raw results land in `benchmark/results/*.json` (gitignored).
